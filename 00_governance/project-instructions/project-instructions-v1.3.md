# Инструкция проекта «Курс „ИИ с нуля“»

*Обязательные правила работы для всех чатов, авторов и редакторов*

**Версия:** 1.3  
**Дата:** 11 сентября 2026 года  
**Статус:** действующим считается экземпляр в `main`; вне `main` — проект или производная bootstrap-копия.

**Назначение.** Этот документ задаёт минимальные обязательные правила работы над проектом. Он используется вместе с актуальным утверждённым документом «Манифест и продуктовые принципы» и утверждёнными архитектурными документами курса. Каноническое состояние проекта хранится в GitHub; общие источники ChatGPT Project не используются как зеркало репозитория.

## 1. Цель проекта

Мы готовим учебный курс по нейросетям и современному ИИ для пользователей нулевого уровня. Работа ведётся в модели профессионального преподавателя с большим опытом погружения новичков в новые темы. Материал должен быть понятен человеку без технической подготовки и формировать практический, переносимый навык, а не знание интерфейса конкретного сервиса.

## 2. Канонические нормативные источники

Рабочий репозиторий проекта:

<https://github.com/Herurg123/Basic-AI-Course>

Ветка `main` является единственным каноническим утверждённым состоянием проекта.

Перед разработкой или проверкой архитектурного документа, урока, упражнения, исследования или производственного материала необходимо читать актуальные версии непосредственно из `main`:

1. актуальную инструкцию проекта в `00_governance/project-instructions/`;
2. `AGENTS.md`;
3. актуальный утверждённый манифест в `00_governance/manifest/`;
4. относящиеся к задаче утверждённые архитектурные и производственные документы.

Копия этой инструкции в общих источниках ChatGPT Project является **bootstrap-копией**: она нужна, чтобы новый чат знал репозиторий, порядок входа и правила работы. Если bootstrap-копия и GitHub расходятся, действующей считается версия в `main`, а расхождение нужно сообщить владельцу проекта.

## 3. Работа с противоречиями

Если в процессе возникает расхождение с базовыми принципами, его нельзя исправлять или обходить молча. Нужно явно указать, какой принцип затронут, в чём состоит расхождение, почему оно возникло и какие варианты решения существуют. Изменение обязательного принципа обсуждается с владельцем проекта и фиксируется новой версией соответствующего нормативного документа.

Если два утверждённых документа в `main` противоречат друг другу, рабочий чат не выбирает удобный вариант молча. Он фиксирует конфликт, определяет уровень затронутого решения и действует по установленной проектной иерархии.

## 4. GitHub как единственное рабочее хранилище проектных документов

GitHub используется как мастер-хранилище и единственный рабочий источник утверждённых проектных документов, истории разработки, веток, изменений, решений и материалов курса.

Общие источники ChatGPT Project **не являются второй библиотекой утверждённых документов и не синхронизируются с GitHub как зеркало**. В них не следует хранить копии документов, которые уже являются каноническими файлами репозитория: манифест, карты, матрицы, стандарты, архитектуру, шаблоны, карточки уроков и другие Git-tracked документы.

Это правило введено специально для устранения риска рассинхронизации двух наборов файлов.

Допустимые исключения для общих источников ChatGPT Project:

- bootstrap-копия актуальной инструкции проекта;
- пользовательские или внешние исходные материалы, которые сознательно не хранятся в GitHub, например крупный архив первичных материалов;
- временные материалы, если владелец проекта явно решил использовать их как источник конкретной задачи.

Такие исключения не становятся каноническими проектными документами автоматически. Если внешний источник существенно влияет на проект, его роль и связь с GitHub-документами должны быть зафиксированы в репозитории.

## 5. Работа только через ветки и Pull Request

Содержательные изменения не вносятся напрямую в ветку `main`. Для каждой самостоятельной задачи создаётся отдельная рабочая ветка. После подготовки изменений открывается Pull Request в `main` с кратким описанием цели, затронутых документов и существенных решений. Ветка `main` рассматривается как утверждённое состояние проекта.

## 6. Автоматический аудит критиком перед merge

Pull Request нельзя сливать в `main` до отдельного критического аудита. После подготовки Pull Request рабочий чат или агент обязан самостоятельно запустить критика без ожидания отдельной команды владельца проекта.

Проверка должна быть отделена от авторского прохода по роли и цели: критик ищет причины не принимать изменение, а не подтверждает вывод автора. Если платформа позволяет использовать отдельный чат, агента, модель или иной независимый проверочный контекст, следует использовать его с максимально доступной глубиной размышления. Если отдельный критик технически недоступен, выполняется отдельный adversarial-проход с явным чек-листом и без опоры на авторское заключение.

Аудит проверяет как минимум:

- соответствие актуальному манифесту;
- сохранность общей архитектуры курса;
- ориентацию на абсолютного новичка;
- отсутствие скрытого усложнения и необоснованных дублей;
- корректность зависимостей между документами;
- сохранение переносимости навыка;
- отсутствие регрессий в ранее утверждённых принципах и компетенциях.

Результат фиксируется в Pull Request как `ОДОБРЕНО` либо как перечень замечаний. Некритические замечания, не требующие проектного решения владельца, исправляются рабочим чатом самостоятельно, после чего аудит запускается повторно.

Если критик одобрил изменение и критических замечаний нет, Pull Request следует сразу слить в `main` без ожидания дополнительного подтверждения владельца проекта.

Если критик выявил критическую проблему, противоречие обязательному принципу или решение, требующее выбора владельца проекта, merge запрещён: нужно сообщить владельцу, что именно не так, какие принципы или документы затронуты и какие варианты решения существуют.

## 7. Форматы рабочих файлов в GitHub

В репозитории рабочие исходники хранятся в форматах, максимально подходящих для Git: они должны быть текстовыми, хорошо сравниваться в diff, удобно редактироваться и позволять видеть историю изменений построчно.

Для текстовых документов основным рабочим форматом является Markdown (`.md`). Для структурированных данных по возможности используются простые текстовые форматы, например CSV, JSON или YAML, если они действительно удобнее для конкретной задачи. Изображения и другие медиа хранятся в подходящих конечных форматах, но не используются как единственный носитель важной текстовой информации.

## 8. Канонический источник и производные форматы

Для текстовых проектных документов версия в GitHub в Git-дружественном формате считается каноническим рабочим исходником, если для конкретного документа явно не зафиксировано иное.

DOCX создаётся дополнительно как производная версия для передачи людям, согласования, печати и подготовки материалов к переносу в Stepik. PDF при необходимости является публикационным или контрольным экспортом, но не рабочим мастер-файлом.

Не следует параллельно независимо редактировать `.md` и `.docx`: изменения сначала вносятся в канонический исходник, после чего производные версии создаются заново. Если правка была сделана человеком только в DOCX, перед следующим merge её нужно перенести обратно в канонический исходник и проверить расхождения.

Производный DOCX/PDF можно скачать, передать или временно использовать вне GitHub, но его не следует помещать в общие источники ChatGPT Project как вторую действующую копию GitHub-документа. Исключение составляет bootstrap-копия этой инструкции.

## 9. Версионирование и тяжёлые файлы

История рабочих версий хранится прежде всего средствами Git: коммитами, ветками, Pull Request и тегами или релизами. Не нужно создавать множество файлов вида `final`, `final2`, `final_really_final`.

Номер утверждённой версии указывается внутри нормативного документа; отдельные архивные снимки при необходимости размещаются в каталоге `releases`.

Крупные бинарные файлы, особенно видео и тяжёлые исходники, не следует без необходимости хранить в обычной истории Git. Для них используется внешнее хранилище или Git LFS, а в репозитории сохраняются ссылки, описание и метаданные, необходимые проекту.

## 10. Правило общих источников ChatGPT Project

Общие источники ChatGPT Project больше **не синхронизируются** с каждым значимым merge.

После перехода на эту версию инструкции в общих источниках должна оставаться только актуальная bootstrap-копия инструкции проекта и осознанно оставленные внешние исходные материалы, которые не дублируют GitHub.

При обновлении самой проектной инструкции действует специальный порядок:

1. новая версия сначала утверждается в GitHub через обычный branch → PR → critic → merge workflow;
2. после merge создаётся производная DOCX-копия этой утверждённой версии;
3. владелец заменяет предыдущую bootstrap-копию инструкции в общих источниках ChatGPT Project новой;
4. предыдущую bootstrap-копию удаляют, чтобы одновременно не существовало нескольких действующих локальных инструкций.

Другие утверждённые GitHub-документы в общие источники после merge не копируются.

Если новый чат видит в общих источниках копию GitHub-документа, отличного от bootstrap-инструкции или явно обозначенного внешнего исходника, он не должен считать её актуальной только потому, что она доступна локально. Действующую версию нужно читать из `main`, а лишний дубликат следует отметить для удаления.

## 11. Правило для новых чатов

Новый чат, который разрабатывает или проверяет часть курса, работает в таком порядке:

1. читает bootstrap-копию этой инструкции в общих источниках ChatGPT Project;
2. открывает репозиторий и читает актуальную инструкцию из `main`;
3. читает `AGENTS.md`, актуальный манифест и относящиеся к задаче утверждённые документы из `main`;
4. проверяет текущее состояние репозитория и не полагается на названия или содержимое старых локальных копий;
5. только после этого начинает содержательную работу.

Новый чат не должен незаметно пересматривать решения проекта внутри собственной задачи. При работе с GitHub он изменяет канонические исходники, а не создаёт конкурирующие версии одного и того же документа.

Если доступ к GitHub или необходимому файлу в `main` технически недоступен, чат не заменяет его предположительно актуальной копией из старого Project Source. Он сообщает владельцу, какого канонического источника не хватает, и останавливает затронутое решение до восстановления доступа или явного решения владельца.

## 12. Антирассинхронное правило

Для любого Git-tracked проектного документа должен существовать один действующий канонический экземпляр: файл в `main`.

Нельзя поддерживать вручную две «актуальные» копии одного и того же нормативного, архитектурного или производственного документа в GitHub и ChatGPT Project Sources.

При обнаружении дубля порядок действий такой:

1. проверить, что нужная утверждённая версия есть в `main`;
2. использовать версию из `main` как источник истины;
3. удалить дублирующую локальную копию из общих источников;
4. если локальная копия содержит уникальную правку, сначала оформить эту правку через GitHub workflow, а не терять её при удалении.

## Короткий обязательный workflow

> **1.** Прочитать bootstrap-инструкцию, затем актуальные нормативные и относящиеся к задаче файлы непосредственно из `main`.
>
> **2.** Определить канонический GitHub-файл, который требуется изменить.
>
> **3.** Создать рабочую ветку под задачу.
>
> **4.** Внести изменение в Git-дружественный канонический исходник и выполнить авторскую проверку.
>
> **5.** При необходимости создать производные DOCX/PDF и другие материалы, но не создавать независимую параллельную редакцию и не добавлять её в Project Sources как зеркало GitHub.
>
> **6.** Открыть Pull Request в `main`.
>
> **7.** Автоматически, без ожидания владельца проекта, запустить отдельный критический аудит Pull Request.
>
> **8.** Если замечания некритические и не требуют проектного решения, исправить их самостоятельно и запустить аудит повторно.
>
> **9.** Если критик дал положительное заключение, сразу выполнить merge в `main` без дополнительного ожидания подтверждения владельца проекта.
>
> **10.** Если критик выявил критическую проблему, не выполнять merge; сообщить владельцу, что именно не так, и вынести на обсуждение варианты решения.
>
> **11.** После merge актуализировать `README.md` и `AGENTS.md`, если изменилось состояние проекта или рабочие правила. Общие источники ChatGPT Project не синхронизировать, кроме замены bootstrap-копии самой проектной инструкции и осознанной работы с внешними исходными материалами.

## История изменений

**v1.0** — зафиксированы GitHub, ветки, Pull Request, независимый аудит и синхронизация с общими источниками.

**v1.1** — зафиксированы Git-дружественные рабочие форматы, Markdown как основной формат текстовых исходников, канонический источник, производные DOCX/PDF, правила синхронизации форматов, версионирования и хранения тяжёлых бинарных файлов.

**v1.3** — GitHub `main` закреплён как единственное каноническое утверждённое состояние проектных документов; прекращено зеркальное хранение нормативных и архитектурных GitHub-документов в общих источниках ChatGPT Project; общие источники оставлены для bootstrap-копии инструкции и осознанных внешних исходных материалов; введено антирассинхронное правило и явный порядок работы нового чата через GitHub.
