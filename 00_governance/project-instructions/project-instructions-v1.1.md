# Инструкция проекта «Курс „ИИ с нуля“»

*Обязательные правила работы для всех чатов, авторов и редакторов*

**Версия:** 1.1  
**Дата:** 10 сентября 2026 года

**Назначение.** Этот документ задаёт минимальные обязательные правила работы над проектом. Он используется вместе с актуальным утверждённым документом «Манифест и продуктовые принципы» и утверждёнными архитектурными документами курса.

**1. Цель проекта**

Мы готовим учебный курс по нейросетям и современному ИИ для пользователей нулевого уровня. Работа ведётся в модели профессионального преподавателя с большим опытом погружения новичков в новые темы. Материал должен быть понятен человеку без технической подготовки и формировать практический, переносимый навык, а не знание интерфейса конкретного сервиса.

**2. Главный нормативный источник**

Базовые принципы и манифест расположены в файле «**Манифест и продуктовые принципы**» в общих источниках проекта. Для всех чатов и работ используется только актуальная утверждённая версия. Перед разработкой или проверкой архитектурного документа, урока, упражнения или исследования необходимо свериться с манифестом.

**3. Работа с противоречиями**

Если в процессе возникает расхождение с базовыми принципами, его нельзя исправлять или обходить молча. Нужно явно указать, какой принцип затронут, в чём состоит расхождение, почему оно возникло и какие варианты решения существуют. Изменение обязательного принципа обсуждается с владельцем проекта и фиксируется новой версией соответствующего нормативного документа.

**4. GitHub как рабочее хранилище проекта**

Рабочий репозиторий проекта: <https://github.com/Herurg123/Basic-AI-Course>

GitHub используется как мастер-хранилище истории разработки: утверждённых документов, рабочих веток, изменений, решений и материалов курса. Общие источники проекта ChatGPT содержат актуальные нормативные и утверждённые документы, необходимые всем чатам.

**5. Работа только через ветки и Pull Request**

Содержательные изменения не вносятся напрямую в ветку main. Для каждой самостоятельной задачи создаётся отдельная рабочая ветка. После подготовки изменений открывается Pull Request в main с кратким описанием цели, затронутых документов и существенных решений. Ветка main рассматривается как утверждённое состояние проекта.

**6. Обязательный независимый аудит перед merge**

Pull Request нельзя сливать в main до отдельной независимой проверки критиком. Критик не должен быть тем же чатом или агентом, который подготовил изменение. Критика можно запускать на независимых мощностях ChatGPT с максимальной доступной степенью размышления и модели, доступной в текущей подписке.

Аудит проверяет как минимум: соответствие актуальному манифесту; сохранность общей архитектуры курса; ориентацию на абсолютного новичка; отсутствие скрытого усложнения и необоснованных дублей; корректность зависимостей между документами; сохранение переносимости навыка; отсутствие регрессий в ранее утверждённых принципах и компетенциях. Результат аудита фиксируется в Pull Request: «одобрено» либо перечень обязательных исправлений. Merge разрешён только после устранения критических замечаний и явного положительного заключения.

**7. Форматы рабочих файлов в GitHub**

В репозитории рабочие исходники хранятся в форматах, максимально подходящих для Git: они должны быть текстовыми, хорошо сравниваться в diff, удобно редактироваться и позволять видеть историю изменений построчно. Для текстовых документов основным рабочим форматом является Markdown (.md). Для структурированных данных по возможности используются простые текстовые форматы, например CSV, JSON или YAML, если они действительно удобнее для конкретной задачи. Изображения и другие медиа хранятся в подходящих конечных форматах, но не используются как единственный носитель важной текстовой информации.

**8. Канонический источник и производные форматы**

Для текстовых проектных документов версия в GitHub в Git-дружественном формате считается каноническим рабочим исходником, если для конкретного документа явно не зафиксировано иное. DOCX создаётся дополнительно как производная версия для передачи людям, согласования, печати и подготовки материалов к переносу в Stepik. PDF при необходимости является публикационным или контрольным экспортом, но не рабочим мастер-файлом. Не следует параллельно независимо редактировать .md и .docx: изменения сначала вносятся в канонический исходник, после чего производные версии обновляются заново. Если правка была сделана человеком только в DOCX, перед следующим merge её нужно перенести обратно в канонический исходник и проверить расхождения.

**9. Версионирование и тяжёлые файлы**

История рабочих версий хранится прежде всего средствами Git: коммитами, ветками, Pull Request и тегами или релизами. Не нужно создавать множество файлов вида final, final2, final_really_final. Номер утверждённой версии указывается внутри нормативного документа; отдельные архивные снимки при необходимости размещаются в каталоге releases. Крупные бинарные файлы, особенно видео и тяжёлые исходники, не следует без необходимости хранить в обычной истории Git. Для них используется внешнее хранилище или Git LFS, а в репозитории сохраняются ссылки, описание и метаданные, необходимые проекту.

**10. Синхронизация утверждённых документов**

После merge значимого нормативного или архитектурного документа в main его актуальная утверждённая версия должна быть размещена или обновлена в общих источниках проекта ChatGPT. В общие источники помещается удобная для использования утверждённая версия; при необходимости это DOCX. Черновики и рабочие варианты в общие источники не добавляются как действующие документы. Канонический рабочий исходник при этом остаётся в GitHub.

**11. Правило для новых чатов**

Новый чат, который разрабатывает или проверяет часть курса, сначала изучает эту инструкцию, актуальный манифест и относящиеся к задаче утверждённые архитектурные документы. Он не должен незаметно пересматривать решения проекта внутри собственной задачи. При работе с GitHub он должен изменять канонические исходники, а не создавать конкурирующие версии одного и того же документа в разных форматах.

**Короткий обязательный workflow**

> **1.** Изучить актуальные проектные источники и определить канонический файл, который требуется изменить.
>
> **2.** Создать рабочую ветку под задачу.
>
> **3.** Внести изменение в Git-дружественный канонический исходник и выполнить авторскую проверку.
>
> **4.** При необходимости обновить производные DOCX/PDF и другие материалы, но не создавать независимую параллельную редакцию.
>
> **5.** Открыть Pull Request в main.
>
> **6.** Передать Pull Request отдельному независимому критику на архитектурный аудит.
>
> **7.** Исправить обязательные замечания.
>
> **8.** Получить положительное заключение критика.
>
> **9.** Только после этого выполнить merge в main, при необходимости создать релизный экспорт и синхронизировать утверждённые документы с общими источниками проекта.
>
> **10.** После каждого Pull Request следует актуализировать файлы README и AGENTS в github – чтобы эти файлы всегда содержали в себе актуальное состояние проекта
