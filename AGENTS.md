# AGENTS.md

Этот файл задаёт краткие рабочие правила для ИИ-агентов и чатов, работающих с репозиторием курса «ИИ с нуля».

## Перед началом работы

1. Если чат запущен внутри ChatGPT Project, прочитать bootstrap-копию инструкции проекта из общих источников.
2. Затем обязательно открыть актуальную инструкцию проекта непосредственно в `00_governance/project-instructions/` ветки `main`.
3. Прочитать актуальный утверждённый манифест в `00_governance/manifest/`.
4. Для архитектурных и производственных задач изучить относящиеся к ним утверждённые документы в `01_architecture/` и других каталогах `main`.
5. Не считать локальную Project Source-копию GitHub-документа актуальной по умолчанию. Каноническое состояние проектных документов находится только в `main`.
6. Не считать авторские статьи или рабочий промпт источником, способным незаметно переопределить утверждённый принцип.

Если необходимый канонический файл в GitHub технически недоступен, не заменять его предположительно актуальной локальной копией: сообщить владельцу и остановить затронутое решение.

## Правила изменений

- `main` содержит только утверждённое состояние проекта.
- Содержательные изменения готовятся в отдельной ветке.
- Текстовые мастер-файлы хранятся в Git-дружественном формате, обычно Markdown.
- DOCX/PDF являются производными версиями для людей, согласования и Stepik и не редактируются независимо от канонического исходника.
- Общие источники ChatGPT Project не используются как зеркало GitHub. В них допускается bootstrap-копия актуальной инструкции и осознанные внешние исходные материалы, которые не дублируют Git-tracked документы.
- Изменения попадают в `main` только через Pull Request.
- После подготовки PR рабочий чат или агент сам запускает отдельный критический аудит без ожидания команды пользователя.
- Критический проход должен быть отделён от авторского по роли и цели. При наличии отдельного чата, агента или модели используется отдельный проверочный контекст; иначе проводится отдельный adversarial-проход с явным чек-листом.
- Критик проверяет соответствие манифесту, целостность архитектуры, ориентацию на абсолютного новичка, переносимость навыков и отсутствие регрессий.
- Некритические замечания исправляются самостоятельно, после чего аудит повторяется.
- Если критик одобрил PR и критических замечаний нет, PR сразу сливается в `main` без ожидания дополнительного подтверждения пользователя.
- Если критик выявил критическую проблему или требуется решение владельца проекта, merge запрещён; проблема и варианты решения сообщаются владельцу.
- После значимого PR актуализируются `README.md` и `AGENTS.md`, если изменилось состояние проекта или рабочие правила.
- После обычного merge не копировать утверждённые GitHub-документы в Project Sources. При изменении самой инструкции после merge обновляется только её bootstrap-копия.

## Явный handoff владельцу для файлов и ручных действий в GitHub

Если дальнейший шаг проекта зависит от действия, которое должен выполнить владелец вручную в GitHub, агент обязан сообщить об этом **явно и до объявления этапа завершённым**. Это относится, в частности, к загрузке документа, изображения, скриншота, бинарника, медиафайла или иного артефакта, который агент не может корректно добавить сам.

Сообщение владельцу должно содержать одновременно:

1. явную пометку, что требуется действие владельца (`OWNER ACTION REQUIRED` или равноценная недвусмысленная формулировка);
2. точную ветку или иной Git-контекст, куда должен попасть файл;
3. точный каталог в репозитории и **кликабельную ссылку** на него;
4. точное имя файла, включая расширение;
5. ожидаемый формат и существенные ограничения файла, если они есть;
6. указание, нужно ли добавить новый файл или заменить существующий;
7. после действия владельца агент обязан самостоятельно проверить, что файл действительно появился в ожидаемом месте, и только после этого снимать blocker/ставить `READY`.

Если файл уже был предоставлен в чате, но для канонического состояния проекта его ещё нужно положить в GitHub, агент обязан сказать об этом отдельно и не считать чат-вложение эквивалентом файла в репозитории.

Нельзя оставлять требуемое от владельца Git-действие только в author notes, hidden checklist, production summary или внутреннем reasoning. Оно должно быть вынесено в обычный ответ владельцу с точным местом назначения.

## Автоматическая гигиена веток

- Ежедневную уборку рабочих веток выполняет `.github/workflows/repository-janitor.yml`.
- Принцип безопасности janitor: любое сомнение, ошибка API, неизвестное состояние или несоответствие ожидаемому SHA означает **сохранить ветку**.
- В штатной конфигурации janitor запускается только по ежедневному `schedule`; ручной `workflow_dispatch` отсутствует, чтобы нельзя было искусственно прокрутить счётчик первых dry-run запусков.
- Workflow имеет жёсткий runtime-замок: cleanup выполняется только в `Herurg123/Basic-AI-Course` и только из `refs/heads/main`.
- Если GitHub сообщает default branch, отличный от `main`, janitor обязан аварийно завершиться без удалений: по проектной инструкции канонической веткой остаётся именно `main`.
- `main`, current default branch, protected-ветки и точные имена из `KEEP_BRANCHES` всегда сохраняются.
- Автоудаление применяется только к явно разрешённым рабочим префиксам, перечисленным в самом workflow. Новые или неизвестные пространства имён по умолчанию сохраняются.
- Текущий allowlist префиксов: `architecture/`, `audit/`, `bootstrap/`, `governance/`, `housekeeping/`, `production/`, `setup/`, `testing/`.
- Ветка с открытым PR или ветка, используемая как base открытого PR, всегда сохраняется.
- Ветка со смёрженным PR в `main` может удаляться только если её текущий SHA точно равен head SHA этого PR, после merge не было новых коммитов и прошёл заданный карантин.
- Ветка без подходящего merged PR может удаляться только если `ahead_by = 0` относительно `main` и прошёл отдельный более длинный карантин.
- Непосредственно перед удалением janitor обязан повторно проверить SHA, protection и открытые PR. Изменение состояния в ходе запуска отменяет удаление.
- Первые **7 ежедневных запусков** workflow всегда выполняются как `DRY-RUN`; без изменения workflow через отдельный PR этот период нельзя прокрутить ручными запусками.
- После dry-run периода действует circuit breaker: не более **5 реальных удалений за один запуск**. Остальные безопасные кандидаты сохраняются до следующего запуска.
- Repository variable `REPOSITORY_JANITOR_FORCE_DRY_RUN=true` является аварийным рубильником: janitor продолжает проверки и формирует Summary, но не удаляет ветки независимо от номера запуска.
- Каждый запуск формирует русскоязычную GitHub Actions Summary: что найдено, что удалено или было бы удалено, что сохранено и почему.
- Нельзя ослаблять критерии удаления, расширять разрешённые префиксы, менять `KEEP_BRANCHES`, карантины, лимит удалений или dry-run период прямой правкой `main`. Такие изменения проходят отдельный branch → Pull Request → критический аудит → merge.
- При расследовании удаления сначала читать Summary соответствующего запуска Actions, затем логи workflow и историю PR/ветки.

## Основной принцип курса

Мы учим пользоваться современным ИИ как классом инструментов. Конкретный сервис используется для практики, но не является содержанием навыка.

## Ограничения Stepik и управление поведением ученика

- Действует [D-2026-09-12-STEPIK-FLOW](00_governance/decision-log/2026-09-12-stepik-advisory-sequencing.md).
- Если Stepik технически не способен надёжно принудить ученика к желательному учебному поведению, отсутствие такого контроля само по себе не считается дефектом курса или критическим blocker. Переход вперёд до выполнения текущего шага — основной текущий пример, но правило не ограничивается только навигацией.
- В таких случаях курс занимает рекомендательную педагогическую позицию: явно говорит, что именно лучше сделать или не делать, и кратко объясняет, почему соблюдение этой рекомендации выгодно самому ученику и сохраняет ценность обучения/самопроверки.
- Аудит оценивает качество такого учебного договора, минимизацию преждевременных подсказок и наличие recovery-route там, где он нужен, а не требует недостижимой платформенной блокировки.
- Если ученик уже нарушил рекомендуемый порядок и увидел существенную подсказку, по возможности используется честный recovery/alternate scenario, а не фиктивное подтверждение самостоятельности.
- Это правило **не ослабляет** содержательные критерии компетенций, privacy/safety, требования к фактически выполненному действию, внешние правила платформ и запрет ложного зачёта навыка.

## Возрастная граница продукта

- Формулировка «понятно даже подростку» относится только к педагогической сложности материала.
- Курс не обещает право доступа к конкретной ИИ-платформе пользователю определённого возраста и не создаёт отдельный child/parent route.
- Возрастные ограничения, согласие законного представителя и иные условия доступа применяет сама сторонняя платформа; курс не учит их обходить.
- Age functional testing не является внутренним Lesson/Service Acceptance/release-gate, если проект отдельно не примет новое решение обещать гарантированный маршрут конкретной возрастной группе.

## Human Pilot / Human Validation

- Действуют [Human Pilot Architecture v1.0](06_testing/human-pilot/human-pilot-architecture-v1.0.md) и утверждённый [Operational Human Pilot Package](06_testing/human-pilot/operational-package/README.md).
- Текущий статус после PR #33 и PR #35: `HUMAN PILOT DESIGNED / OPERATIONAL PACKAGE APPROVED / NOT YET PERFORMED`; human validation = `NOT PERFORMED` до фактических сессий с реальными novice users.
- Model/synthetic pre-pilot, ИИ-симуляция или ещё один модельный аудит не считаются human validation.
- Human pilot обязан допускать провал курса. Модератор не должен спасать level-3/F1 попытку содержательной подсказкой ради PASS.
- `N/P/T/C/S` — обязательная taxonomy вмешательств: technical/interface help (`T`) логируется и допустима по контракту; substantive/content help (`C`) загрязняет текущую independent attempt и переводит её в `PRACTICE / CONTAMINATED`; safety stop (`S`) имеет приоритет над чистотой evidence.
- Post-hoc объяснение не создаёт отсутствующее прошлое действие и не восстанавливает independence после content hint.
- B3 проверяется фактическим privacy-действием **до** transfer; B8 — реальным edit существующего исходника, не regeneration; B10 — реальным открытым/сопоставленным основанием, не self-check/второй моделью; B12/F1 — фактическим применением результата, не ответом, оставшимся в чате.
- `M07-L02-C01` остаётся единственным F1 INDEPENDENT level 3. Модератор может проверить только допустимость/посильность/безопасность задачи, но не выбирать задачу, маршрут, источник, правку или способ применения за ученика.
- Content hint во время F1 аннулирует independent status этой задачи; для чистого F1 нужна другая новая реальная посильная задача.
- Полный Human Pilot PASS требует наблюдения private Stepik staging; content-only прогон может дать максимум `PARTIAL — STEPIK UX NOT VALIDATED`.
- Operational package уже прошёл branch → PR #35 → adversarial critic → merge и не должен производиться заново без нового основания. До Wave 0 нужно фактически подтвердить private Stepik staging, consent/data-minimization в рабочей среде, moderator rehearsal, recovery readiness и актуальный service preflight.
- Пока readiness-пункты не подтверждены evidence, Wave 0 не считается `READY`; approval package сам по себе не является human validation.
- Human Pilot PASS не равен closed beta и не разрешает автоматически public release. Closed beta и финальные динамические Stepik/service checks остаются последующими gates.
