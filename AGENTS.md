# AGENTS.md

Этот файл задаёт краткие рабочие правила для ИИ-агентов и чатов, работающих с репозиторием курса «ИИ с нуля».

## Перед началом работы

1. Если чат запущен внутри ChatGPT Project, прочитать bootstrap-копию инструкции проекта из общих источников.
2. Затем обязательно открыть актуальную инструкцию проекта непосредственно в `00_governance/project-instructions/` ветки `main`.
3. Прочитать актуальный утверждённый манифест в `00_governance/manifest/`.
4. Для архитектурных и производственных задач изучить относящиеся к ним утверждённые документы в `01_architecture/` и других каталогах `main`.
5. Не считать локальную Project Source-копию GitHub-документа актуальной по умолчанию. Каноническое состояние проектных документов находится только в `main`.
6. Не считать авторские статьи или рабочий промпт источником, способным незаметно переопределить утверждённый принцип.

Если необходимый канонический файл в GitHub технически недоступен, не заменять его предположительно актуальной локальной копией: сообщить владельцу и остановить затронутое решение.

## Правила изменений

- `main` содержит только утверждённое состояние проекта.
- Содержательные изменения готовятся в отдельной ветке.
- Текстовые мастер-файлы хранятся в Git-дружественном формате, обычно Markdown.
- DOCX/PDF являются производными версиями для людей, согласования и Stepik и не редактируются независимо от канонического исходника.
- Общие источники ChatGPT Project не используются как зеркало GitHub. В них допускается bootstrap-копия актуальной инструкции и осознанные внешние исходные материалы, которые не дублируют Git-tracked документы.
- Изменения попадают в `main` только через Pull Request.
- После подготовки PR рабочий чат или агент сам запускает отдельный критический аудит без ожидания команды пользователя.
- Критический проход должен быть отделён от авторского по роли и цели. При наличии отдельного чата, агента или модели используется отдельный проверочный контекст; иначе проводится отдельный adversarial-проход с явным чек-листом.
- Критик проверяет соответствие манифесту, целостность архитектуры, ориентацию на абсолютного новичка, переносимость навыков и отсутствие регрессий.
- Некритические замечания исправляются самостоятельно, после чего аудит повторяется.
- Если критик одобрил PR и критических замечаний нет, PR сразу сливается в `main` без ожидания дополнительного подтверждения пользователя.
- Если критик выявил критическую проблему или требуется решение владельца проекта, merge запрещён; проблема и варианты решения сообщаются владельцу.
- После значимого PR актуализируются `README.md` и `AGENTS.md`, если изменилось состояние проекта или рабочие правила.
- После обычного merge не копировать утверждённые GitHub-документы в Project Sources. При изменении самой инструкции после merge обновляется только её bootstrap-копия.

## Автоматическая гигиена веток

- Ежедневную уборку рабочих веток выполняет `.github/workflows/repository-janitor.yml`.
- Принцип безопасности janitor: любое сомнение, ошибка API, неизвестное состояние или несоответствие ожидаемому SHA означает **сохранить ветку**.
- `main` и текущий default branch никогда не являются кандидатами на удаление. Protected-ветки и точные имена из `KEEP_BRANCHES` также всегда сохраняются.
- Автоудаление применяется только к явно разрешённым рабочим префиксам, перечисленным в самом workflow. Новые или неизвестные пространства имён по умолчанию сохраняются.
- Ветка с открытым PR или ветка, используемая как base открытого PR, всегда сохраняется.
- Ветка со смёрженным PR в default branch может удаляться только если её текущий SHA точно равен head SHA этого PR, после merge не было новых коммитов и прошёл заданный карантин.
- Ветка без подходящего merged PR может удаляться только если `ahead_by = 0` относительно default branch и прошёл отдельный более длинный карантин.
- Непосредственно перед удалением janitor обязан повторно проверить SHA, protection и открытые PR. Изменение состояния в ходе запуска отменяет удаление.
- Первые **7 запусков** workflow всегда выполняются как `DRY-RUN`; способа обойти этот защитный период через input нет.
- Каждый запуск формирует русскоязычную GitHub Actions Summary: что найдено, что удалено или было бы удалено, что сохранено и почему.
- Нельзя ослаблять критерии удаления, расширять разрешённые префиксы, менять `KEEP_BRANCHES`, карантины или dry-run период прямой правкой `main`. Такие изменения проходят отдельный branch → Pull Request → критический аудит → merge.
- При расследовании удаления сначала читать Summary соответствующего запуска Actions, затем логи workflow и историю PR/ветки.

## Основной принцип курса

Мы учим пользоваться современным ИИ как классом инструментов. Конкретный сервис используется для практики, но не является содержанием навыка.
