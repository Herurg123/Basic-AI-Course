## 1. Правило наследования

Human Pilot Architecture v1.1 **не переписывает историю и не заменяет полный текст v1.0**. Все содержательные правила v1.0 сохраняются без ослабления, если ниже явно не указано точечное уточнение.

В частности, без изменений действуют:

- обязательность реального Human Pilot до human validation;
- проверка на screened novice users, а не модельная симуляция;
- требования F1 к новой реальной задаче и фактическому применению результата;
- уровни самостоятельности и запрет содержательной помощи в независимой попытке;
- правила contamination: загрязнённая попытка становится тренировочной и требует новой ситуации;
- наблюдаемое evidence вместо факта просмотра, ответа модели или самоотчёта задним числом;
- recovery как содержательно новая ситуация, а не повтор известного ответа;
- неизменность PASS/FAIL-логики: технический или модельный успех не превращается автоматически в human PASS.

Если формулировка v1.0 и этот point update читаются как конфликт, решение не выбирается молча: применяется порядок Project Instructions v1.4 и конфликт выносится владельцу.

## 3. Уровни доказательства: статусы не взаимозаменяемы

Для readiness используются пять разных классов доказательства:

- **SOURCE PASS** — канонический исходник/сборочная спецификация соответствует требованию;
- **MACHINE PASS** — автоматизированная проверка или read-back доказала конкретное машинно наблюдаемое состояние;
- **HUMAN VISUAL PASS** — человек проверил фактически видимый learner-facing интерфейс/маршрут;
- **SERVICE PASS** — требуемое действие реально выполнено в актуальном сервисе на проверяемом бесплатном маршруте;
- **HUMAN VALIDATION PASS** — реальный screened novice выполнил требуемое действие с допустимой самостоятельностью и evidence.

Один класс доказательства **не подменяет** другой. В частности:

- SOURCE PASS не доказывает, что материал опубликован, видим или кликабелен;
- MACHINE PASS не доказывает понятность новичку;
- документация сервиса не является SERVICE PASS;
- HUMAN VISUAL PASS автора/владельца не является HUMAN VALIDATION PASS;
- зелёный workflow не доказывает эквивалентность всего курса `main`, если workflow проверял или менял ограниченный scope.

## 5. Regression contract после Astra

Merge source-исправлений PED-01…PED-07 через PR #59 означает только принятие канонической подготовки. Он не закрывает реальные gates автоматически.

Перед Wave 0 readiness review обязательно отдельно подтвердить:

1. source regression PED-02, PED-04 и PED-05 на актуальном `main`;
2. реальный device gate PED-01 на desktop и phone;
3. SERVICE PASS PED-03 на актуальных бесплатных маршрутах;
4. публикационный HUMAN VISUAL PASS PED-06;
5. learner-facing HUMAN VISUAL PASS PED-07 на реально собранном private Stepik;
6. эквивалентность предъявляемого private Stepik staging принятой версии курса;
7. сохранение author-only boundaries, recovery visibility и advisory sequencing;
8. отсутствие содержательного загрязнения independent attempts, включая CRIT-C-01.

Любая последующая production/Stepik правка, способная затронуть эти поверхности, требует повторной проверки соответствующего gate. Старое доказательство не переносится на изменённый объект автоматически.

## 6. Stepik staging как объект Human Pilot

Human Pilot проводится не «по репозиторию», а по конкретному private staging, который реально увидит участник.

До первой human session должны быть одновременно известны:

- source `main` SHA, относительно которого собран staging;
- course ID и подтверждение private state;
- доказательство соответствия canonical lessons, порядка модулей/уроков и learner-facing title/body;
- подтверждённые physical assets и learner routes;
- machine state/PENDING без необъяснённого хвоста относительно выбранного source SHA;
- Human Visual checks там, где machine evidence недостаточно;
- current service preflight.

Если machine state показывает `PENDING` относительно выбранного канона, либо доказана только часть уроков, staging имеет статус **NOT READY / BLOCKED** для первой human session, даже если отдельные workflows завершились `success`.

## 7. Wave 0 допускается только после полного operational gate

Сохраняется требование v1.0: Wave 0 — это первая проверка на двух eligible novice participants, а не способ выяснить, собран ли вообще курс.

До Wave 0 должны быть закрыты как минимум:

- private staging equivalence;
- physical asset materialization и publication checks;
- PED-01 desktop/phone route;
- PED-03 live service generation/edit;
- PED-06/PED-07 publication visual checks;
- recovery/author-only visibility;
- consent и data-minimization operational setup;
- moderator rehearsal;
- current service preflight;
- наличие двух eligible Wave 0 participants.

Если любой из этих пунктов не имеет фактического evidence, он остаётся `NOT READY`/`BLOCKED`; tooling или план выполнения не являются PASS.

## 8. Что этот update не меняет

v1.1 не изменяет:

- 9 модулей и 21 Lesson ID;
- компетенции и уровни самостоятельности;
- F1;
- screened novice definition;
- wave design;
- minimum evidence;
- severity model;
- contamination/retest rules;
- правила privacy/data minimization;
- запрет объявлять `HUMAN VALIDATED` без фактического Human Pilot.

Историческая Human Pilot Architecture v1.0 остаётся в репозитории неизменной. Текущая нормативная точка входа — этот v1.1 вместе с наследуемым полным текстом v1.0.
