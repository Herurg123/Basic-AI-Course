# План подготовки материалов для проведения пилота

**Pilot Execution Blueprint v1.0 · 12 сентября 2026 года**  
**Статус:** `HUMAN PILOT DESIGNED / NOT YET PERFORMED`.  
**Base main:** `84446b74cc230f174fca735893bd0ad7456b10f6`.

Следующий production-исполнитель готовит по этому документу операционный пакет для реальных модераторов и участников. Здесь определены состав, поля, владельцы и порядок использования. **Заполненных форм, результатов участников и готового набора анкет в этом этапе нет.**

Обязательные основания: [архитектура](human-pilot-architecture-v1.md), [Gate](human-pilot-gate-v1.md), [гипотезы](pilot-critical-hypotheses-v1.md). Формы не имеют права создавать новый F1-алгоритм, подсказывать проверяемые решения или менять рубрику курса. Статус `DESIGNED` не означает `READY TO RUN`.

## 1. Общие правила всех материалов

Разделить три слоя: learner-facing организационные материалы; закрытые observer/reviewer материалы; разрешённый к GitHub обезличенный отчёт. Название поля не должно незаметно превращать observer-критерий в подсказку ученику.

Для событий и наблюдений использовать единые ключи: `Participant ID`, `Wave`, `Course commit`, `Build ID`, `Protocol version`, `Session ID`, `Lesson ID`, `Check ID`, `Attempt ID`, `Parent attempt ID`, `Device class`, `Service route`, `Event time`. Не все поля повторяются вручную в каждой форме: общие значения наследуются из заголовка сессии.

`Attempt ID` идентифицирует наблюдение, не заменяет Check ID курса. У каждой попытки отдельны process status и assessment status. Разрешены пустые неприменимые поля с причиной; неизвестное обозначается `UNKNOWN`, не нулём и не PASS. Строки с данными никогда не заполняются «типичными ответами» за человека.

Ссылки на закрытое evidence — внутренние идентификаторы без публичных signed URL. Уникальные названия личных задач, контакты и скриншоты могут повторно идентифицировать человека даже без имени. Заполненный пакет хранится вне GitHub; туда допускаются только подготовленные безопасные формы без данных и reviewed aggregate findings.

| Материал | Назначение и обязательные поля | Кто и когда | Запреты |
|---|---|---|---|

| Contamination and recovery log | Exposure/content event ID, момент относительно действия/критерия, affected Check/construct, исходный статус, recovery source, новизна, parent/new attempt IDs, prerequisite impact, новый исход | Модератор сразу после события; reviewer до зачёта | Удаление первой неудачной попытки; косметический повтор; новый зачёт по той же раскрытой задаче |

| Competency/evidence ledger | Все required Check IDs по Coverage Assessment; target level; факт/артефакт, pre/post раскрытие, применимость, assessment/process statuses; кто оценил; ссылки на составные B10/C2 и prerequisites F1 | Observer после каждой проверки, reviewer до F1/итогов | Компенсацию слабой компетенции сильной; quiz/баллы Stepik вместо действий; B0 как уровень 3 |
| Lesson-level issue log | Finding ID, lesson/step, тип, H0–H3, механизм, observation refs, affected/exposed distinct participants, версии, источник COURSE/SERVICE/PROTOCOL/PARTICIPANT/MIXED/UNRESOLVED, альтернативное объяснение, owner, решение | Pilot lead после сессии и при повторении; немедленно для H0/H1 | Уникальные личные истории в публичной сводке; «участник плохой» без evidence |

## 5. Отдельный комплект F1

F1 observation form — **только для модератора/reviewer**, не дополнительная ученическая форма. Ученик использует штатную post-action A03 после работы. Production-исполнитель не создаёт до попытки формуляр «цель → критерии → контекст → проверка → применение».

Обязательные поля observer F1 form:

- Participant/attempt/version и ссылки на **все** prerequisite checks, составные B10/C2 и M07-L01;
- кто предложил задачу; безопасное описание реального назначения; прежняя экспозиция/новизна; admissibility decision и точная реплика модератора;
- время начала, самостоятельного объявления завершения, раскрытия A03/критериев, каждого help/exposure события;
- ссылки на естественный pre-rubric trace собственных решений и pre-evaluation образа пригодности; отсутствие trace отдельным статусом;
- применимые измерения штатной A02 с evidence и основанием каждого N/A; completion/application всегда обязательны;
- первая и конечная версия при реальной доработке, выбранные основания/статусы при необходимости, связь статуса с действием;
- наблюдаемый конечный результат и actual application, время и способ безопасного подтверждения;
- safe stop/change, continuation vs new task, contamination scope, parent attempt и новая собственная задача;
- независимые оценки модератора и reviewer, расхождения и окончательное основание PASS/NOT PROVEN/PRACTICE/NOT COMPLETED.

Не собирать полную личную задачу, если безопасного описания и наблюдения достаточно. Если доказать применение без лишней передачи данных не удаётся, выбирать безопасный способ наблюдения; не вынуждать публикацию или сообщение третьим лицам. Нельзя помогать содержательно для того, чтобы форма наконец заполнилась.

## 7. Порядок подготовки пакета

1. Прочитать утверждённый дизайн и текущий main; проверить, изменились ли production или внешняя среда. Отдельно выяснить статус O-HP-01 и назначение реальных людей/хранилища.
2. Создать рабочую ветку operational package. Зафиксировать Course commit и mapping learner/author views без изменения уроков по вкусу.
3. Подготовить screener, consent, организационный минимум, unified observer log и поля F1/reviewer; затем формы triage и summary. Формы остаются пустыми.
4. Проверить learner view и техническую пригодность среды. При прототипе сформировать deviations list; это ещё не Stepik validation.
5. Провести калибровку персонала и проверить, что форма не подсказывает решение. Для F1 особенно проверить, что observer form недоступна до попытки.
6. Проверить entry Gate построчно. Нерешённые реальные prerequisites оставить блокерами. Не начинать приглашения/сессии автоматически от создания форм.
7. Открыть PR пакета и запустить отдельного критика по governance. После утверждения выполнять только согласованный следующий этап; pilot results ведутся по закрытому data contract.

## 8. Критерий готовности operational package

Другой подготовленный модератор должен по документам понять: кого включать, какую версию показывать, когда молчать и помогать, что считать C-помощью, как остановить попытку, какую новую ситуацию выдать, что сохранить и как принять решение. Пустые формы согласованы по ID/status/time и не дублируют обязательную запись вручную.

Пакет проходит review только при работающем безопасном сборе evidence, достаточной роли доступа и явной границе learner/author. Готовность форм не снимает ограничения выборки или O-HP-01. Никакая заполненная строка со словом PASS не добавляется до соответствующего фактического наблюдения.

## 9. Сохранение и продолжение после остановки исполнителя

После каждого законченного этапа подготовки сохранять в рабочую ветку соответствующие документы и обновлять [RESUME](RESUME.md): что завершено, что не проверено, исходный/main и рабочий HEAD, PR, reviewer verdict, открытые owner decisions, следующий конкретный шаг. Проверять успешную запись в GitHub; локальные изменения сами по себе не контрольная точка.

Во время будущего реального пилота запись после каждой сессии сохраняется в закрытом хранилище исследования, с контрольным подтверждением сохранения и удалением случайных персональных данных. GitHub получает только безопасный статус и обезличенные conclusions после review. При возобновлении не восстанавливать потерянные participant observations по памяти и не повторять раскрытую задачу ради зачёта.
